# MPZ Log Viewer

## Общее описание проекта

- Утилита для чтения и анализа лог-файлов МПЗ (mpz.log). 
- Парсит структурированные логи Java-приложения, выделяет процессы МПЗ и позволяет фильтровать/просматривать их.

### Сборка и закпуск:

- Платформа: Java 8 (target 1.8).
- Сборка и зависимости: Maven.
- GUI: GUI-only на JavaFX 8, встроенная в JDK 8 — запуск окна только под JDK/JRE 8. 
- Тесты: JUnit.
- `mvn clean package` дополнительно собирает `.exe` через launch4j. `.exe` собирается с GUI-заголовком (`headerType=gui`).
  ```bash
  mvn clean package
  java -jar target/mpz-log-viewer-1.0.0.jar                     # GUI (главный класс gui.GuiApp), только JDK 8
  ```

### Структура:

- `gui/GuiApp.java` — главный класс (JavaFX): тулбар (комбо «Отображение») + центральный список содержимого файла; слева — список процессов МПЗ с фильтром («Только ошибочные» / «Все с PID» / «Все процессы»); внизу — панель частых ошибок и статус-бар. При запуске сразу запрашивается открытие лог-файла (при отмене приложение завершается). Статус-бар показывает путь к файлу, размер, дату создания, количество строк/процессов/ошибок. Стили — `src/main/resources/gui/app.css` (плоская современная тема вместо дефолтных градиентов Caspian). Между запусками сохраняется положение/размер окна и состояние «максимизировано/обычное» (`GuiSettings`, Windows Preferences/реестр); при максимизации обычные (немасимизированные) границы не перезаписываются.
- `gui/GuiSettings.java` — сохранение состояния GUI (последняя папка, границы и состояние «максимизировано/обычное» окна) через `java.util.prefs.Preferences`
- `parser/MpzLogParser.java` — парсер лога (строки → `LogEntry`)
- `model/LogEntry.java` — модель записи лога
- `model/LogModel.java` — модель лога МПЗ: список элементов Процесс + список Все Строки лога
- `model/ProcessElement.java` — элемент Процесс (PID, processName, Status, трэд последнего запроса, подчинённые Строки и Ошибки); `pidLabel()`, `firstLineNumber()`
- `model/LogLine.java` — элемент Строка лога (запись + признак request/response)
- `model/ErrorElement.java` — элемент Ошибка (Полный текст, Ключ, Краткий текст)
- `model/LogModelBuilder.java` — построение модели единым проходом по записям лога

## Модель

### Формат лога МПЗ

- Записи лога МПЗ делять на записи процессов и прочие записи
- Записи процессов в свою очередь делятся на 
  - Запросы, которые имею вид `... handle-request: <?xml...><process-instance>XXXXX</process-instance>...`
  - Ответы, которые имеют вид `... handle-response: <?xml...><process-instance>XXXXX</process-instance>...`
- Процес начинается с `handle-request` где `<process-instance>=0`. Ответ содержит реальный PID процесса.
- Последующий ответ будет содержать PID процесса.
- Повторный вызов к уже известному процессу: `handle-request` с `process-instance=<PID>`.
- Прочие записи относятся к запросу с одинаковым тредом, где task — имя треда, `default task-N`.
- Записи системных ошщибок — первая строка сообщения содержит `Exception` и не начинается с `Caused by`.

### Модель лога МПЗ

- Модель лога МПЗ должна содержать список элементов Процесс.
- Каждый элемент Процесс должна иметь поля: PID, processName, Status, Трэд последнего найденного запроса (для сопоставления с Прочими записями) 
- К каждому элементу Процесс сдолжны быть подчинены элементы Строка лога (все строки относящиеся к процессу).
- К каждому элементу Процесс должны быть подчинены элементы Ошибка
  - Элемент Ошибка должен иметь поля: Полный текст ошибки, Ключ ошибки, Краткий текст ошибки
    - Полный текст ошибки — вся запись лога целиком включая стэктреёс.
    - Краткий текст ошибки — все строки до первой `at `, не являющейся `at by.softclub.mpz.` (включается mpz-стектрейс).
  - Ключ ошибки это краткий текст, который маскируется: цифры → `#`, строковые SQL-параметры `'...'` → `'?'`, подряд идущие пробелы схлопываются;
    коды `ORA-XXXXX` не маскируются.
- Модель лога МПЗ должна иметь список Все Строки лога.

### Алгоритм построения модели лога МПЗ

Единственный проход по всем записям лога:
- Добавить запись во список Все строки.
- ЕСЛИ это запись Запроса:
  - ЕСЛИ `handle-request pi=0` — старт нового процесса: создать элемент Процесс (в статусе `UNRESOLVED`), добавить в список Процессов.
  - ЕСЛИ `handle-request pi=PID` — повторный вызов: если процесс с таким PID известен, запись идёт в него.
    Поле `task` процесса обновляется на трэд последнего запроса (чтобы прочие записи и ошибки с этим трэдом попадали в него).
    - ИНАЧЕ создать новую запись Процесса с найденным PID.
- ЕСЛИ это запись ответа `handle-response`:
  - ЕСЛИ PID ответа ≠ 0 и процесс с таким PID известен, ТО добавить в найденный Процесс;
  - ЕСЛИ PID ответа ≠ 0 и процесс с таким PID нет, ищем Процесс с равным трэдом, в котром PID = 0, значит это ответ на первый запрос.
  - ИНАЧЕ ответ непривязанный, добавляем новый Процесс.
- ЕСЛИ запись является системной ошибкой, добавить ее в Процесс и подчинённые к нему Ошибки. Посчитать ключ ошибки.
- ЕСЛИ это прочая запись, добавить в Процесс с равным трэдом.

Расчёт статуса Процесса (`Status`):
- `COMPLETED` — получен PID и response с `<result><type>END_OF_PROCESS</type></result>` (штатное успешное завершение);
- `COMPLETED_WITH_ERROR` — получен PID и response с `<result><type>ERROR</type></result>` (штатное завершение с прикладной ошибкой);
- `INTERRUPTED` — получен PID, но response с `END_OF_PROCESS` или `ERROR` не найден (процесс до конца не дошёл, прерван);
- `FAILED` — получена любая системная ошибка на любом из шагов, процесс до конца не дошёл; 
- `UNRESOLVED` — response не найден (запрос не завершился ответом);
- Статус `COMPLETED` и `COMPLETED_WITH_ERROR` не понижаются последующими ответами (повторные вызовы к завершённому процессу).

- Если запрос не завершился своим response, хвостовые записи треда последнего запроса включаются в процесс, но
  обрезаются на первом request другого процесса с тем же task.
- Если стартовый request получил ответ с уже известным PID — новый процесс сливается с существующим.

## GUI

Приложение GUI-only (`gui/GuiApp`, JavaFX 8). Принцип работы: открытие лог-файла → парсинг
(`MpzLogParser`) → построение модели (`LogModelBuilder`) → отображение. Стили — `gui/app.css`
(плоская современная тема вместо дефолтных градиентов Caspian).

### Раскладка окна

`BorderPane`: сверху `ToolBar`, слева — панель процессов, по центру — список строк файла,
снизу — панель «Частые ошибки» над статус-баром. Ширина левой панели ≈ 15% окна, высота
нижней ≈ 25% (слушатели `widthProperty`/`heightProperty` сцены).

- Тулбар: комбо «Отображение» («Все строки» / «Выбранный процесс»), разделитель.
- Левая панель: заголовок «Процессы МПЗ», комбо «Фильтр» («Только ошибочные» / «Все с PID» /
  «Все процессы»), таблица процессов.
- Центр: `ListView<String>` — содержимое файла (место-заглушка до открытия).
- Низ: `TextArea` «Частые ошибки» (топ-10 уникальных ошибок по маскированному ключу
  `ErrorElement.getErrorKey()`, формат `<N> раз(а) — <1-я строка ошибки>`, строки-продолжения
  с отступом) и статус-бар.

### Обработка открытия файла

При запуске сразу вызывается `openFile()` → `FileChooser` (стартовая папка — последняя из
`GuiSettings`); при отмене приложение завершается (`Platform.exit()`). Далее путь записывается
в `currentPath`, `updateFileInfo()` выводит в статус-бар путь, размер и дату создания → инкремент
`openSeq` → два фоновых демон-потока:

- чтение сырых строк (`loadRawContent`) в `allRawLines` и `ListView`;
- разбор и анализ (`analyzeFile`): `MpzLogParser.parse` → `LogModelBuilder.build` →
  `model.getProcesses()`/`getAllLines()`, список процессов с ошибками, затем в статус-бар —
  число строк/процессов/ошибок, `populateProcessList()`, `updateErrorsPanel()`.

Каждый поток возвращает результат в `Platform.runLater` только при `seq == openSeq` (при
повторном открытии файла устаревшие потоки игнорируются). Состояние сбрасывается на старте
анализа: `allProcesses`/`errorProcesses`/`activeProcess`/таблица/панель ошибок.

### Таблица процессов

`TableView<ProcessElement>`, режим одиночного выбора. Колонки: Иконка (цветной кружок по статусу,
`statusIcon()`), PID (`Consolas 11`, `PID: <PID>` через `pidLabel()`, без PID — `PID: #0`), Имя
процесса, «Запросов/ответов» (ширина 52, справа). Статус — только в Tooltip колонки PID.
Активный процесс подсвечивается через PseudoClass `:active-process` (CSS).

Фильтры: «Только ошибочные» (процессы с `errors`), «Все с PID» (у `pid != null`), «Все процессы».
По умолчанию при открытии файла выбирается «Только ошибочные», если есть ошибочные процессы,
иначе «Все процессы».

- Одиночный клик — `showProcessStart()`: центральный список переходит на первую физическую
  строку процесса (поиск совпадения строки в `ListView`).
- Двойной клик — `toggleActiveProcess()`: включает режим «Выбранный процесс».

### Режимы отображения

Комбо «Отображение» в тулбаре. «Все строки» — в центре весь файл (`allRawLines`), активный
процесс сбрасывается. «Выбранный процесс» — `showProcessLines()` выводит только строки процесса:
для каждой записи процесса берутся физические строки файла от её номера до номера следующей
записи (охватывает строки-продолжения многострочных записей/стектрейсов). Повторный двойной
клик или выбор «Все строки» возвращает полный лог.

### Прочее

- Клавиши: Ctrl+O — открыть файл, Ctrl+Q — выйти, Ctrl+C — копировать выделенные строки
  центрального списка в буфер обмена.
- Контекстное меню центрального списка: «Копировать».
- Состояние окна (позиция/размер/максимизировано) сохраняется между запусками через
  `GuiSettings` (Windows Preferences); при максимизации обычные границы не перезаписываются.
  При восстановлении границы проверяются на попадание в видимую область экрана и минимум 300×200.
- Иконка приложения рисуется кодом (WritableImage).

## Известные ограничения

- Для процессов с `pi=0` в response (ошибка) — две записи с `pi=0` (request и response)
- Процессы, не получившие response (в т.ч. на границах обрезанного лога), помечаются `[без ответа]`
- Процессы, получившие PID, но не дошедшие до `END_OF_PROCESS`, помечаются `[прерван]` (например, на границе обрезанного лога)
- GUI требует JDK/JRE 8: JavaFX 8 не входит в Java 11+
