# MPZ Log Viewer — Agent Context

## Project Overview

Утилита для чтения и анализа лог-файлов МПЗ (MpzLog). Парсит структурированные логи Java-приложения, выделяет процессы МПЗ и позволяет фильтровать/просматривать их.

**Сборка:** Maven, Java 8 (target 1.8). GUI использует JavaFX 8, встроенную в JDK 8 — запуск окна только под JDK/JRE 8. 
**Структура:**
- `CliParser.java` — парсинг CLI-аргументов
- `ModeOptions.java` — хранилище опций режима
- `App.java` — CLI-точка входа
- `LogProcessor.java` — общий конвейер обработки (проверка файла → парсинг → ProcessAnalyzer → запуск режима); используется и CLI, и GUI
- `gui/GuiApp.java` — главный класс (JavaFX): тулбар (Открыть файл / Процесс / Список процессов / Grep / Выйти, с векторными иконками) + TextArea вывода; внизу над статус-баром — панель поиска («Поиск:» + поле ~1/4 ширины окна (мин. 100 px) + «Далее» / «Предыдущий»), выделяет найденную строку в выводе; Ctrl+F — фокус в поле поиска; заголовок окна — «MPZ Log Viewer» (без имени файла), иконка приложения рисуется программно. Стили — `src/main/resources/gui/app.css` (плоская современная тема вместо дефолтных градиентов Caspian). Между запусками сохраняется положение/размер окна и состояние «максимизировано/обычное» (`GuiSettings`, Windows Preferences/реестр); при максимизации обычные (немасимизированные) границы не перезаписываются.
- `gui/GuiSettings.java` — сохранение состояния GUI (последняя папка, границы и состояние «максимизировано/обычное» окна) через `java.util.prefs.Preferences`
- `mode/ModeHandler.java` — интерфейс режима
- `mode/ModeContext.java` — контекст для режимов
- `mode/ModeFactory.java` — фабрика, выбирающая режим по `ModeOptions`
- `mode/AnalyzeMode.java` — режим `-a` (по умолчанию): сводка + ошибки по процессам
- `mode/GrepMode.java` — режим `-g`: поиск процессов по тексту
- `mode/ListProcessesMode.java` — режим `-lp`: список процессов
- `mode/ProcessMode.java` — режим `-p`: записи конкретного процесса + итог
- `parser/MpzLogParser.java` — парсер лога
- `parser/LogEntry.java` — модель записи лога
- `parser/ProcessAnalyzer.java` — анализатор процессов МПЗ (строит дерево элементов)
- `parser/Element.java` — базовый класс элемента дерева модели лога
- `parser/LogElement.java` — лист дерева: одна запись лога (обычная/handle)
- `parser/ProcessElement.java` — узел-процесс МПЗ (PID, status, дерево элементов, счётчики)
- `ui/TerminalPrinter.java` — вывод в консоль, файл и GUI (через `PrintWriter`); `processLabel` — единый формат идентификатора процесса

## CLI Arguments

| Флаг | Описание |
|------|----------|
| `-h`, `--help` | Справка |
| `-a`, `--analyze` | Сводная информация о логе (по умолчанию) |
| `-p`, `--process <id>` | Показать записи процесса МПЗ |
| `-g`, `--grep <text>` | Поиск процессов по тексту в записях |
| `-lp`, `--list-processes` | Список процессов МПЗ (с пометкой статуса; процессы без PID — `PID: #0 ...`) |
| `-of`, `--output-file` | Сохранить вывод в файл (плоский текст) |

Для режима `-g` выходной файл имеет суффикс `_grep_<текст>.txt`, где символы, недопустимые в именах файлов (`<>:"/\|?*` и контрольные символы), заменяются на `_`.

Если не указан ни один режим, по умолчанию используется `-a` (`ModeOptions.isDefault()`).

## ProcessAnalyzer — Алгоритм

### Формат лога МПЗ

Записи процесса МПЗ выглядят так:
```
... handle-request: <?xml...><process-instance>0</process-instance>...
... handle-response: <?xml...><process-instance>XXXXX</process-instance>...
```

Процесс начинается с `handle-request` где `<process-instance>=0`. Ответ содержит реальный PID процесса.
Если процесс не может определить PID (ошибка), ответ также содержит `process-instance=0`.
Повторный вызов к уже известному процессу: `handle-request` с `process-instance=<PID>`.

### Модель результата — дерево элементов

Результат анализа — модель лога в виде дерева элементов (`ProcessAnalyzer.getRoot()`),
плюс плоский список процессов (`getProcesses()`).

- `Element` — базовый класс узла.
- `LogElement` — лист: одна запись лога (обычная, handle-request или handle-response; для handle хранит PID из записи).
- `ProcessElement` — узел-процесс: PID (может быть `null`), processId (имя из XML), task (тред старта), статус
  и дерево `children` в порядке лога (request → записи → response). Для удобства режимов ведётся и плоский
  `allEntries` с счётчиками `entryCount`/`reqRespCount`.

Статусы процесса (`ProcessElement.Status`):
- `COMPLETED` — получен PID из ответа;
- `FAILED` — ошибка: на стартовый request пришёл response с `process-instance=0`, PID так и не появился;
- `UNRESOLVED` — response не найден (запрос не завершился ответом); в процесс включены хвостовые записи того же треда.

Единый формат вывода процесса в режимах `-a`, `-lp`, `-g`: `PID: <process-instance> (<process-id>)` — сначала PID,
затем имя процесса в скобках. Процессы без PID выводятся как `PID: #0 (<process-id>)` (`ProcessElement.pidLabel()`).
Строка идентификатора формируется единой функцией `TerminalPrinter.processLabel(pid, pname)` (PID + имя в скобках,
при `pname == null` — `?`); её используют и `printProcessLine` (`-lp`, `-g`), и `printProcessHeader` (`-a`).
В строке процесса (`-lp`, `-g`) после счётчика запросов/ответов выводится номер первой строки журнала,
относящейся к процессу: `первая строка: #N` (`ProcessElement.firstLineNumber()` — номер строки первой записи процесса).

Процессы без PID — отдельные записи с пометкой статуса (в `-lp` выводится `PID: #0 (<process-id>) [статус]`).

### Алгоритм (один проход + стек открытых окон на треде)

Единственный проход по всем записям. Для каждого треда (task — имя треда, `default task-N`) ведётся стек
«открытых окон» — процессов, чей request уже встречен, а response ещё нет. Обычные записи атрибутируются
верхнему элементу стека треда.

- **`handle-request pi=0`** — старт нового процесса: создать `ProcessElement` (status `UNRESOLVED`), добавить
  в плоский список и в корень дерева, положить на стек треда.
- **`handle-request pi=PID`** — повторный вызов: если процесс с таким PID известен, запись идёт в него,
  процесс кладётся на стек треда (записи между ним и ответом попадают в него). Иначе запись атрибутируется
  текущему открытому процессу треда (если есть).
- **`handle-response`** — определить владельца ответа:
  - PID ответа ≠ 0 и процесс с таким PID известен → владелец — этот процесс;
  - иначе по совпадению `process-id` среди открытых окон треда берётся самый старый процесс с таким же
    `process-id` (FIFO: старты могут идти вперемешку, поэтому ответ относится к старейшему, а не к последнему
    открытому процессу); если совпадения нет — самый старый открытый процесс треда;
  - иначе ответ непривязанный.
  Для старейшего процесса `pi` ответа и есть найденный PID: `pi≠0` → статус `COMPLETED`, `pi=0` → статус
  `FAILED`.
  После ответа закрывается окно владельца и все **более старые** открытые окна треда (они уже не получат
  ответ); младшие окна остаются открытыми — их собственные ответы ещё придут, и записи между ними продолжают
  атрибутироваться.
- **Обычные записи** (не handle): атрибутируются верхнему (последнему) открытому процессу треда (между request
  и следующим response). Если открытого окна нет — запись непривязанная (попадает в корень дерева).

### Особенности

- Повторные запросы/ответы с одним и тем же PID относят к одному процессу (включая записи между ними).
- Ответ с неизвестным PID атрибутируется **самому старому** открытому процессу треда с тем же `process-id`
  (FIFO), а не последнему открытому — старты процессов могут идти вперемешку.
- Если запрос не завершился своим response, его хвостовые записи того же треда включаются в процесс, но
  обрезаются на первом response другого процесса с тем же task (окно старее владельца закрывается).
- Если стартовый request получил ответ с уже известным PID — новый процесс сливается с существующим
  (`mergeInto`), из списка/корня удаляется.

## AnalyzeMode — формат вывода

```
═════════════════════════════════════════════
 MPZ Log Viewer
═════════════════════════════════════════════
  Процессов МПЗ: <N>
  Всего строк: <N>
  Критических ошибок: <N>
  Время парсинга: <N> мс

═════════════════════════════════════════════
  Часто встречающиеся ошибки          ← только если criticalErrors > 0
═════════════════════════════════════════════
<N> раз(а) — <1-я строка ошибки в маскированном виде>
             <следующие строки ошибки до начала стектрейса>

═════════════════════════════════════════════
  Ошибочные процессы МПЗ:            ← только если criticalErrors > 0
═════════════════════════════════════════════
PID: <PID> (<process-name>)
<timestamp> <LEVEL> (<thread>) <exception-message>
  <ORA-...>
  <at by.softclub.mpz....>            ← стек до первого non-mpz вызова
─────────────────────────────────────────────
PID: <PID> (<process-name>)
...
```

В блоке «Часто встречающиеся ошибки» каждая уникальная ошибка выводится один раз с общим количеством. Учитывается весь текст ошибки (`AnalyzeMode.errorText`) — все строки сообщения вплоть до начала стектрейса (первой строки, начинающейся с `at `). Ключ ошибки маскируется (`AnalyzeMode.normalizeKey`): цифры → `#`, строковые SQL-параметры в одинарных кавычках `'...'` → `'?'`, подряд идущие пробелы схлопываются; коды ошибок `ORA-XXXXX` не маскируются и остаются неизменными. Поэтому ошибки одного типа, отличающиеся только параметрами/числами, группируются вместе. В выводе секции печатается весь использованный многострочный маскированный текст (продолжения строк — с отступом). Количество выводится в начале строки, выровнено вправо по 3 знака (`String.format("%3d раз(а) — ...")`). Двойные кавычки (например, имена колонок в ORA-сообщениях) не маскируются.

## Сборка и запуск

Сборка и GUI-запуск выполняются под JDK 8 (JavaFX 8 встроена в JDK 8). `mvn clean package` дополнительно собирает `.exe` через launch4j (требует Java 8+). `.exe` собирается с GUI-заголовком (`headerType=gui`) — при запуске консольное окно не показывается, сразу открывается главное окно.

```bash
mvn clean package
java -jar target/mpz-log-viewer-1.0.0.jar                     # GUI (главный класс gui.GuiApp), только JDK 8
java -cp target/mpz-log-viewer-1.0.0.jar com.mpzlog.App mpz.log          # CLI: анализ (по умолчанию)
java -cp target/mpz-log-viewer-1.0.0.jar com.mpzlog.App mpz.log -lp      # CLI: список процессов
java -cp target/mpz-log-viewer-1.0.0.jar com.mpzlog.App mpz.log -p 8092830 -of   # CLI: процесс в файл
java -cp target/mpz-log-viewer-1.0.0.jar com.mpzlog.App mpz.log -a -of    # CLI: анализ в файл
java -cp target/mpz-log-viewer-1.0.0.jar com.mpzlog.App mpz.log -of       # CLI: анализ в файл
```

## Известные ограничения

- Для процессов с `pi=0` в response (ошибка) — две записи с `pi=0` (request и response)
- Процессы, не получившие response (в т.ч. на границах обрезанного лога), помечаются `[без ответа]`
- GUI требует JDK/JRE 8: JavaFX 8 не входит в Java 11+
- Вывод в консоль на Windows может не отображать кириллицу (зависит от кодировки терминала); в GUI кириллица отображается корректно
